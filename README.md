# NativeImageProcessor

An Android app that does image and video processing in **C++ through the NDK**. Kotlin handles the
Jetpack Compose UI; the pixel work runs in native code.

- **Image filters (C++):** grayscale, bilinear resize, and blur. Each runs directly on
  `android.graphics.Bitmap` pixels through `AndroidBitmap_*` / JNI.
- **Video watermark (FFmpeg + C++):** re-encodes a video with a text watermark in the bottom-right
  corner and an icon in the centre. It uses the device's hardware H.264 encoder and copies the
  audio through unchanged.

```
┌────────────────────────────┐
│                            │
│           VIDEO            │
│             ✓              │   ← icon (centre)
│                            │
│                  CeylonAPZ │   ← text (bottom-right)
└────────────────────────────┘
```

## Getting started

1. **Clone the project:**
   ```bash
   git clone https://github.com/amalskr/NativeImageProcessor.git
   ```
2. **Get the FFmpeg libraries.** The app links against prebuilt FFmpeg libraries in
   `app/src/main/cpp/ffmpeg/`. If that folder is missing, build them (about 10 minutes per ABI):
   ```bash
   scripts/build_ffmpeg.sh              # arm64-v8a + x86_64
   ```
   On Windows, run this from **Git Bash**. No WSL or MSYS2 is needed. See
   [Building FFmpeg](#building-ffmpeg).
3. **Open the project in Android Studio and run the `app` configuration**, or build from the
   command line:
   ```bash
   ./gradlew :app:installDebug
   ```

In the app:

- **Image tab:** Pick Image → *Grayscale*, *Resize 50%*, or *Blur* (radius 1–25). Operations
  apply one after another to the image shown; *Reset* returns to the original.
- **Video tab:** Pick Video → *Add Watermark* (shows progress) → a preview plays → *Save* writes
  the MP4 to a location you choose.

## Native API

Everything is exposed through `NativeImageProcessor`. It loads `libnative-image-processor.so`, and
the Android linker loads the FFmpeg libraries it depends on automatically.

```kotlin
val processor = NativeImageProcessor()
```

### Image filters

```kotlin
// In place. The bitmap must be mutable ARGB_8888. Returns null if the format is unsupported.
fun toGrayscale(bitmap: Bitmap): Bitmap?

// Return a NEW bitmap; the source is never modified. Return null on invalid input.
fun resize(bitmap: Bitmap, width: Int, height: Int): Bitmap?
fun blur(bitmap: Bitmap, radius: Int): Bitmap?
```

All three expect `ARGB_8888`. They block the calling thread, so call them from
`Dispatchers.Default`.

### Video watermark

```kotlin
fun addVideoWatermark(
    inputPath: String,               // any path FFmpeg can open, e.g. "/proc/self/fd/<fd>"
    outputPath: String,              // .mp4 to write
    layers: List<WatermarkLayer>,    // blended in order
    marginPx: Int,                   // distance from the edges for corner positions
    listener: ProgressListener?      // progress 0..1, on the calling thread
): String?                           // null = success, otherwise an error message

class WatermarkLayer(val bitmap: Bitmap, val position: WatermarkPosition)
enum class WatermarkPosition { BOTTOM_RIGHT, CENTER }
fun interface ProgressListener { fun onProgress(progress: Float) }
```

> ⚠️ **`null` means success.** Don't chain the result with `?:` after a nullable call such as
> `openFileDescriptor(...)?.use { ... } ?: "error"`. Doing so turns every successful run into an
> error.

This call blocks until it finishes, so run it off the main thread. Layer bitmaps must be
`ARGB_8888` and drawn in **display orientation**, i.e. the way the video looks when played.

To open a `content://` Uri, such as one from the photo picker:

```kotlin
context.contentResolver.openFileDescriptor(uri, "r")?.use { pfd ->
    processor.addVideoWatermark("/proc/self/fd/${pfd.fd}", out.path, layers, margin, listener)
}
```

## How it works

### Image filters (`native_image_processor.cpp`)

- **Pixels:** each filter locks the `Bitmap` pixels with `AndroidBitmap_lockPixels` and walks rows
  using `info.stride`, because rows can be padded. Pixels are premultiplied RGBA stored as bytes
  `R,G,B,A` (so `0xAABBGGRR` as a little-endian `uint32_t`).
- **Grayscale:** integer BT.601 luma, `(77R + 150G + 29B) >> 8`, keeping the original alpha.
- **Resize:** creates the output `Bitmap` from C++ through JNI (`Bitmap.createBitmap`), then does
  centre-aligned bilinear interpolation per channel.
- **Blur:** three separable box-blur passes, which closely approximate a Gaussian blur. Each pass
  uses a sliding window, so the cost doesn't depend on the radius. Edges are clamped.

### Video watermark (`video_watermark.cpp`)

```
mov/mp4 ──demux──► H.264/HEVC decoder (FFmpeg, software)
                        │
                        ▼
                swscale → NV12 ──► alpha-blend overlays (C++) ──► h264_mediacodec (hardware)
                                                                           │
audio packets ──────────────── copied unchanged ─────────────────► mp4 muxer ◄┘
```

1. **Watermark images:** Kotlin draws the text (white, bold, soft shadow, 6% of the video's
   shorter side) and the icon (white silhouette with a dark edge, 12% of the shorter side) into
   bitmaps. Both are sized from the video's display dimensions, read with
   `MediaMetadataRetriever`.
2. **Overlay prep:** C++ converts each layer to limited-range YUV plus alpha once, before
   processing any frames. It uses BT.709 or BT.601 depending on the video, and averages alpha over
   each 2×2 block for the 4:2:0 chroma planes.
3. **Rotation:** phone videos are usually stored sideways with a *display matrix* tag. Each overlay
   is mapped into the stored frame's orientation (0/90/180/270°) so it lands in the right place
   when the video plays. The tag is copied to the output.
4. **Per frame:** decode → `swscale` to NV12 (converting full-range `yuvj420p` from phone cameras
   to limited range) → blend each overlay → send to the encoder.
5. **Encoding:** `h264_mediacodec` uses the device's hardware H.264 encoder. The bitrate follows
   the source (clamped to 1–40 Mbps).
6. **Muxing:** audio streams are copied into the MP4 without re-encoding. Subtitle and data
   streams are dropped.

**Encoder details that matter on real devices:**

- **Frame rate:** phone cameras record at a variable frame rate, and `av_guess_frame_rate()` can
  report 120 fps for a 30 fps clip. Hardware encoders reject that at 1080p, so the encoder is
  given the stream's *average* frame rate, capped at 60, and retries at 30 fps if it's refused.
- **No `AV_CODEC_FLAG_GLOBAL_HEADER`:** with this flag, `h264_mediacodec` encodes a dummy frame
  and then flushes the codec, after which some Codec2 encoders stop producing output. Without it,
  SPS/PPS arrive in the first packet, and the MP4 muxer builds the `avcC` box from that.
- **Busy encoder:** `EAGAIN` from `avcodec_send_frame` means MediaCodec's input queue is full.
  The pipeline collects the encoded output, then retries.
- **Logging:** FFmpeg's log output is routed to logcat under the tag `FFmpeg`, at warning level.
  Encoder settings are logged under `VideoWatermark`.

## Building FFmpeg

`scripts/build_ffmpeg.sh` builds a **minimal LGPL** FFmpeg 8.1.3 as shared libraries, using only
what the app needs:

| Component | Enabled |
|---|---|
| Libraries | `avcodec`, `avformat`, `avutil`, `swscale` |
| Protocol | `file` |
| Demuxer / muxer | `mov` / `mp4` |
| Decoders | `h264`, `hevc` |
| Encoder | `h264_mediacodec` (with `--enable-jni --enable-mediacodec`) |
| Parsers / BSFs | `h264`, `hevc`, `aac` / `extract_extradata`, `h264_metadata`, `*_mp4toannexb` |

```bash
scripts/build_ffmpeg.sh                          # default: arm64-v8a x86_64
scripts/build_ffmpeg.sh armeabi-v7a x86          # other ABIs
ANDROID_NDK_HOME=/path/to/ndk API=24 JOBS=8 scripts/build_ffmpeg.sh
```

- **Output:** `app/src/main/cpp/ffmpeg/{include,lib/<abi>}`. Sources and intermediates go to
  `.ffmpeg-build/`, which is git-ignored.
- **Other ABIs:** if you build more ABIs, add them to `ndk.abiFilters` in `app/build.gradle.kts`.
- **Page size:** the libraries are 16 KB page-aligned, which is NDK 28's default and required on
  newer Android versions.

**On Windows**, the script runs under Git Bash with the NDK's own `make.exe`. It handles:

- **Temp directory:** sets a POSIX `TMPDIR`.
- **Paths:** converts paths with `cygpath -m`, and rewrites the source path that configure records
  so the native `make.exe` can read it.
- **Host compiler:** uses the Android target `clang` as configure's "host compiler". This minimal
  build never runs host programs.
- **Headers:** copies the public headers itself. `make install-headers` exceeds the Windows
  command-line length limit and silently installs nothing.

Don't edit the script while it's running, and don't leave a shell open inside `.ffmpeg-build/`
(Windows locks the folder).

## Testing on a device

Test on a **real phone**. The emulator uses software codecs, and those hide hardware-encoder
problems such as the frame-rate issue above.

```bash
adb devices
./gradlew :app:installDebug
adb logcat -s VideoWatermark FFmpeg     # watch the watermark pipeline
```

**Faster single-ABI builds:** pass `-Pandroid.injected.build.abi=arm64-v8a`. The APKs then go to
`app/build/intermediates/apk/...` instead of `outputs/`.

**On Windows Git Bash**, set `MSYS_NO_PATHCONV=1` before running `adb shell` commands with device
paths such as `/sdcard/...`. Otherwise Git Bash rewrites them as Windows paths.

**Xiaomi / HyperOS phones:** in *Developer options*, turn on **Install via USB**, and tap
*Install* on the phone when prompted. For `adb shell input` automation, also turn on
**USB debugging (Security settings)**.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `UnsatisfiedLinkError: No implementation found for ...` | The JNI function name must match the Kotlin package, e.g. `Java_com_ceylonapz_nativeimageprocessor_NativeImageProcessor_<method>` |
| `undefined symbol: AndroidBitmap_*` when linking | Link `jnigraphics`; each `find_library` call finds one library only |
| `'libavutil/samplefmt.h' file not found` | FFmpeg headers are incomplete. Re-run `scripts/build_ffmpeg.sh` |
| `Cannot open H.264 encoder` | The encoder rejected the size or frame rate. Check the `VideoWatermark: Encoder:` log line against the device's limits in `/vendor/etc/media_codecs*.xml` |
| `INSTALL_FAILED_USER_RESTRICTED` | Xiaomi: turn on *Install via USB* and accept the prompt on the phone |
| Watermark or icon drawn far too large and cropped | Drawing a density-tagged bitmap with `drawBitmap(bmp, x, y)` rescales it. Draw into an explicit `Rect` |

## Known limitations

- **HDR:** 10-bit HDR video is converted to 8-bit SDR, so colours look washed out.
- **Speed:** decoding is software-only, so long 4K videos are slow. Output is always H.264.
- **Resolution:** output keeps the source resolution. Devices whose encoder can't handle it (for
  example 4K on a 1080p-only encoder) will fail with `Cannot open H.264 encoder`.
- **Input formats:** only MP4/MOV/3GP input containers are enabled.
- **Blurry icon:** `copyright.png` is 32 px and gets enlarged. A ≥128 px PNG in
  `drawable-nodpi/`, or a vector drawable, gives sharper edges.
- **32-bit devices:** not packaged by default (`armeabi-v7a`, `x86`).
